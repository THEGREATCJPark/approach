## 요청과 다른 해석

“공방의 소수 재료 사용료가 행별 합계와 전체 합계에서 1단위 다르게 나온다.”

- 반올림 시점 정책이 서로 다르다.
- 이진 부동소수점 표현이 경계 판정을 흔든다.
- 재처리한 행이 중복 정산된다.

## 우선 질문과 방향 변화

1. 행별 반올림인가 최종 합계 반올림인가? → 둘을 계산해 차이를 보이고 정책 하나를 확정한다.
2. 0.5 처리 규칙은 무엇인가? → 이 연습은 HALF_UP이며 은행식 반올림으로 추정하지 않는다.
3. 음수 환급도 같은 정책인가? → 허용 범위와 사유 필드를 별도 정한다.

파일에서 이미 확인되는 답은 다시 묻지 않는다. 정책을 결정할 권한자와 기준 시점을 함께 기록한다.

## 데이터 계약과 합성 입력

사용 한 행. line_id 기본키, quantity 소수 문자열 kg, rate 소수 문자열 가상 정산단위/kg. 양수 사용만 허용. 각 행 원금=quantity×rate, 최종 합계를 정수단위 HALF_UP.

최소 필수는 아래 판정 필드와 키다. 대표 샘플·스키마로 시작하며 개인 식별 정보는 필요하지 않다. 개선용 데이터는 실제 작업 시간과 오류 기록이다. 전체 이력이나 외부 API는 첫 검증에 없어도 된다. null은 미확인이며 0·false와 다르다. 필수 필드가 없으면 해당 판정을 보류하고 담당자 확인 목록에 남긴다.

## 기준 방법, 제약과 최소 경로

Decimal을 문자열에서 생성하고 계산을 유지한다. 최종 반올림과 행별 반올림의 차이를 별도 출력한다. 큰 금액·긴 소수 입력은 precision과 허용 자릿수를 먼저 고정한다.

필수: finite 값, 중복 line_id 거절, quantity≥0, rate≥0, 누락 시 합계 보류. 최적화 목적은 없다. 정책 결정 전 두 합계를 혼합하지 않는다.

사용표 → 정확 원금과 두 정산안 → 최종6,행별7 → 정책 담당자가 기준을 확정하고 차이 원인을 설명한다.

## 기대 결과와 반례

| 유형 | 입력 또는 변경 | 기대 결과 |
|---|---|---|
| 정상 | 기본 다섯 행 | 원금6.000,최종6,행별7 |
| 경계 | quantity0.125 rate12 한 행 | 1.5→2 |
| 정보 부족 | quantity=null | 합계 보류,0 대체 금지 |
| 충돌 | quantity=-0.1 | 양수 사용 계약 위반 |
| 중복 | line_id a 반복 | 중복 입력 오류 |
| 새 샘플 | quantity0.124 rate12 한 행 | 1.488→1 |

손계산 근거: 원금은1.5+1.5+2.4+0.6+0=6.0. 행별 HALF_UP은2+2+2+1+0=7. 0.124×12=1.488은1이다.

비슷하지만 다른 두 건: 0.125kg와0.124kg는0.001kg 차이지만 정수 정산은2와1이다. 경계 차이를 버그로 단정하지 않는다.

작은 계산 예제는 [check_c.py](../../examples/synthetic/check_c.py)에서 별도 표준 라이브러리 계산으로 확인한다. 각 수용 테스트 행의 기대값은 소형 오라클 계산으로 확인한다. 전체 앱·화면·DB 동시성은 구현하거나 검증하지 않았으며, 기대값 검증과 구현물 테스트 통과는 다르다. 실행 범위는 해당 스크립트 출력과 검증 보고서를 따른다.

## 답변이 바뀌면 수정할 계획

- 행별 정산으로 바뀌면 합계7을 정본으로 바꾸고 원금6은 참고값으로 남긴다.
- 환급이 허용되면 음수 수량 정책과 원 거래 연결키를 추가한다.

## 피할 구현과 축소 기준

- 시세·환율 기준 시점 문제를 반올림 수정만으로 해결하지 않는다.
- float에서 Decimal로 변환하거나 표시 문자열을 다시 계산하지 않는다.
- 시간 부족이면 통화 연동 대신 정확 원금·정산 정책·차이표를 유지한다.

1순위 도구는 [Python 표준 라이브러리](../../tools/python-stdlib.md)다. 이 작은 합성 입력에는 패키지 설치·외부 호출이 필요 없다. Python도 실행할 수 없으면 표에 후보를 전부 적고 손계산한다. 대규모 개선 도구는 설치·규정·입력 적합성이 확인된 이후 별도 선택한다.
