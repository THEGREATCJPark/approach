## 요청과 다른 해석

“체험실에서 방문자가 고른 관심사에 맞는 관찰 키트 두 개를 안내하고 싶다.”

- 사용 가능 여부와 관심 일치가 주된 결정이다.
- 실제 문제는 재고 최신성일 수 있다.
- 여러 사람에게 동시에 배정해야 한다면 추천이 아니라 자원 배정이다.

## 우선 질문과 방향 변화

1. 추천 후 실제 재고를 확정하는가? → 안내만이면 조회, 확정이면 별도 원자적 예약을 설계한다.
2. 미확인 재고를 노출해도 되는가? → 확인 필요 목록과 확정 추천을 분리한다.
3. 관심 태그가 없는 방문자는 어떻게 처리하는가? → 가용 항목 ID 순 기본 목록을 표시하고 개인화라고 부르지 않는다.

파일에서 이미 확인되는 답은 다시 묻지 않는다. 정책을 결정할 권한자와 기준 시점을 함께 기록한다.

## 데이터 계약과 합성 입력

키트 한 행. id 문자열 기본키, available 정수 개수, restricted 불리언, tags 문자열 배열. 요청은 interests 집합, k 정수. 재고 기준 시각은 실제 운영에서 필수다.

최소 필수는 아래 판정 필드와 키다. 대표 샘플·스키마로 시작하며 개인 식별 정보는 필요하지 않다. 개선용 데이터는 실제 작업 시간과 오류 기록이다. 전체 이력이나 외부 API는 첫 검증에 없어도 된다. null은 미확인이며 0·false와 다르다. 필수 필드가 없으면 해당 판정을 보류하고 담당자 확인 목록에 남긴다.

```json
[
  {
    "id": "A",
    "available": 2,
    "restricted": false,
    "tags": [
      "빛",
      "물"
    ]
  },
  {
    "id": "B",
    "available": 0,
    "restricted": false,
    "tags": [
      "빛",
      "식물"
    ]
  },
  {
    "id": "C",
    "available": 1,
    "restricted": true,
    "tags": [
      "물"
    ]
  },
  {
    "id": "D",

      "식물"
    ]
  },
  {
    "id": "E",
    "available": null,
    "restricted": false,
    "tags": [
      "빛"
    ]
  }
]
```

## 기준 방법, 제약과 최소 경로

available > 0 및 restricted = false를 먼저 필터링한다. 관심 집합 {빛,물}과 교집합 크기 내림차순, 동점 id 오름차순으로 정렬한다. 개선은 명시적 선호를 받은 뒤 가중치 비교다.

필수: 가용·제한 확인. 선호: 관심 일치 수. 금지 항목은 점수가 높아도 복귀시키지 않는다. 목적은 확정 가능한 후보 중 일치도를 정렬하는 것이며 대여 완료를 의미하지 않는다.

키트 JSON → 필터 사유 목록 → 추천 A,D와 점수 2,0 → 담당자가 재고 확인 후 안내한다.

## 기대 결과와 반례

| 유형 | 입력 또는 변경 | 기대 결과 |
|---|---|---|
| 정상 | 관심 {빛,물}, k=2 | A,D; 점수 2,0 |
| 경계 | k=0 | 빈 추천, 오류 아님 |
| 정보 부족 | E available=null | E는 보류, 추천 제외 |
| 충돌 | 모든 항목 restricted=true | 추천 없음; 조건 충돌 안내 |
| 순서변경 | 입력 행을 역순 | 추천 A,D 유지 |
| 새 샘플 | F 가용1 제한false tags=[물] 추가 | A,F |

손계산 근거: A 교집합={빛,물}이므로 2, D는 공집합이므로 0. B 재고0, C 제한, E 미확인으로 탈락한다. F는 1이므로 D보다 앞선다.

비슷하지만 다른 두 건: 재고 0은 사용 불가, null은 확인 보류다. 둘 다 추천에서 빠지지만 안내 사유는 달라야 한다.

작은 계산 예제는 [check_c.py](../../examples/synthetic/check_c.py)에서 별도 표준 라이브러리 계산으로 확인한다. 각 수용 테스트 행의 기대값은 소형 오라클 계산으로 확인한다. 전체 앱·화면·DB 동시성은 구현하거나 검증하지 않았으며, 기대값 검증과 구현물 테스트 통과는 다르다. 실행 범위는 해당 스크립트 출력과 검증 보고서를 따른다.

## 답변이 바뀌면 수정할 계획

- 재고 확정 필요로 바뀌면 추천과 예약을 분리하고 예약 시 재검증한다.
- 태그가 목표가 아니라 숙련도 안전 기준이면 숙련도 필터를 필수조건으로 추가한다.

## 피할 구현과 축소 기준

- 여러 요청의 공동 배정 또는 시간별 예약을 이 단순 순위로 풀지 않는다.
- 임베딩 추천을 먼저 설치하거나 미확인 재고를 0으로 저장하지 않는다.
- 시간 부족이면 개인화 가중치는 빼고 가용 필터와 제외 이유를 유지한다.

1순위 도구는 [Python 표준 라이브러리](../../tools/python-stdlib.md)다. 이 작은 합성 입력에는 패키지 설치·외부 호출이 필요 없다. Python도 실행할 수 없으면 표에 후보를 전부 적고 손계산한다. 대규모 개선 도구는 설치·규정·입력 적합성이 확인된 이후 별도 선택한다.

## 연습 시간 예산과 효과 측정

30분: 다섯 행 필터 손계산. 90분: 입력·추천·보류 표. 180분: 재고 시각과 담당자 피드백 반영. 권장 연습 예산이다.

가용하지 않은 추천 수/전체 추천 수와 추천 후 재확인 건수를 측정할 수 있다. 이 합성 예제만으로 실제 조직의 시간 절감·만족도·수익 향상을 주장할 수 없다.
