## 1. 창작 업무 요청

“새 방문자에게 보여줄 시설 안내 카드가 필요한데 개인 이력이 없다.”

## 2. 다른 원인과 목표

- 개인화 없이 집계 반응률에 근거한 기본 순위를 정한다.
- 노출 위치가 반응률 차이를 만들었을 수 있다.
- 적은 노출의 우연한 높은 반응이 순위를 왜곡할 수 있다.

## 3. 먼저 확인할 질문과 분기

1. 개인화가 필요한가 기본 순위면 되는가? → 기본이면 개인 로그 수집을 제외한다.
2. 노출 집계의 위치·기간이 같은가? → 다르면 순위를 보류하고 층별 비교한다.
3. 초기 완화값을 정할 수 있는가? → 합의된 가상 성공1/실패1을 쓰고 다른 값 민감도를 비교한다.

자료에서 이미 확인되는 답은 다시 묻지 않는다. 정책 답변이 충돌하면 기준 시점과 결정 권한을 확인하고 기존 가정을 기록한다.

## 4. 데이터 계약

카드 한 행: id 문자열 키, impressions 비음수 정수 회, clicks 정수 회(0~impressions). comparable 불리언은 동일 집계 조건 확인 여부. (clicks+1)/(impressions+2)는 순위 점수이며 개인의 확률 추정 보장이 아니다.

위 필드는 최소 필수다. 운영 중 오류·수동 수정 기록은 개선에 유용하고 전체 개인 이력은 첫 실험에 필요하지 않다. 필수 값이 null이면 미확인으로 처리하며 0이나 false로 바꾸지 않는다. 자료를 받을 수 없으면 아래 합성 입력으로 계산만 확인하고 실제 판정은 보류한다.

```json
{
  "comparable": true,
  "items": [
    [
      "A",
      10,
      4
    ],
    [
      "B",
      2,
      1
    ]
  ]
}
```

## 5. 기준 방법과 개선 조건

동일 조건일 때 완화 반응률을 분수로 비교하고 동점은 id 오름차순으로 둔다. 신규 카드 0회도 1/2 점수를 받으므로 탐색 노출 정책을 별도로 합의한다. 개선은 무작위 노출 실험 후 위치 효과를 통제하는 것이다.

1순위 도구는 [Python 표준 라이브러리](../../tools/python-stdlib.md)다. 설치 없이 작은 목록·집합·정수 연산으로 시작한다. 실행이 허용되지 않거나 Python이 없으면 후보 표와 손계산을 남긴다. 외부 API·자격증명은 필요 없다. 복잡한 패키지는 데이터 크기와 실패 사례가 기준 방법의 한계를 보여준 뒤 검토한다.

## 6. 최소 구현과 다음 행동

집계표 → 조건 확인 → A/B 점수와 기본 순위 → 운영자가 제한된 시험 노출 목록을 선택한다.

완료 기준은 실제 입력 한 건에서 판정·근거·미확인 사유·다음 행동이 이어지는 것이다. 합성 테스트 통과는 실제 사용자 만족이나 업무 효과를 입증하지 않는다.

## 7. 정상·경계·정보 부족 기대값

| 유형 | 입력 | 기대 결과 | 독립 계산 근거 |
|---|---|---|---|
| normal | `{"comparable":true,"items":[["A",10,4],["B",2,1]]}` | `["B", "A"]` | A=5/12, B=2/4; B가 높다. |
| boundary | `{"comparable":true,"items":[["A",0,0],["B",0,0]]}` | `["A", "B"]` | 둘 다1/2, id로 동점 정리. |
| missing | `{"comparable":null,"items":[["A",10,4]]}` | `"unknown"` | 비교 가능 조건이 미확인이다. |

[실행 오라클](../../examples/synthetic/check_expansion_c.py)은 각 기대값을 다시 계산한다. 이는 문서 기대값 검증이며 완성 앱·동시 사용자·현장 운영 테스트가 아니다.

## 8. 잘못된 적용과 범위 축소

- 노출 조건이 다른 집계로 인기도를 확정하지 않는다.
- 가상 성공·실패 수를 실제 관측 수처럼 표시하지 않는다.

시간이 부족하면 장식·선택 기능을 줄이고 입력 계약, 미확인 처리, 위 기대값 검증을 유지한다. 효과는 동일 업무의 전후 완료 시간·오류 수와 측정 대상 수를 확보한 뒤 판단한다.

## 9. 구현물에 대한 사용자 피드백

1. 기본 순위와 점수의 근거를 보고 실제 노출 여부를 정할 수 있는가?
2. 새 카드의 적은 근거가 화면에서 충분히 드러나는가?

설명 전에 사용자가 한 건을 처리하게 하고 실패·우회·추가 질문을 관찰한다. 새 요구를 오류 수정·필수 누락·선택 개선으로 분류한다.

1. 왜 클릭 수 자체 대신 분모와 완화값을 함께 사용했는가?
