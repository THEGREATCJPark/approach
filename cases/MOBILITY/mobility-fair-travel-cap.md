## 1. 창작 업무 요청

“이용자들을 두 서비스 지점에 배정하되 누구도 이동시간 상한을 넘지 않게 하고 싶다.”

## 2. 다른 원인과 목표

- 평균 최소 대신 개인별 상한을 필수조건으로 둔다.
- 지점 정원 때문에 가장 가까운 곳에 모두 배정할 수 없다.
- 이용자별 이동수단이 다르면 공통 행렬이 잘못될 수 있다.

## 3. 먼저 확인할 질문과 분기

1. 상한은 반드시 지켜야 하는가? → 필수면 초과 배정을 만들지 않고 불가능을 표시한다.
2. 지점 정원은 동시 정원인가 하루 처리량인가? → 시간단위가 다르면 시간대 배정이 필요하다.
3. 미배정 허용 정책이 있는가? → 없으면 전체 가능성을 먼저 확인한다.

자료에서 이미 확인되는 답은 다시 묻지 않는다. 정책 답변이 충돌하면 기준 시점과 결정 권한을 확인하고 기존 가정을 기록한다.

## 4. 데이터 계약

이용자 한 행 [id,[지점별분]], capacity는 지점별 정수 명, cap은 개인 이동분 상한. 이용자 id 고유, 행렬열은 capacity순. 개인정보는 필요없다.

위 필드는 최소 필수다. 운영 중 오류·수동 수정 기록은 개선에 유용하고 전체 개인 이력은 첫 실험에 필요하지 않다. 필수 값이 null이면 미확인으로 처리하며 0이나 false로 바꾸지 않는다. 자료를 받을 수 없으면 아래 합성 입력으로 계산만 확인하고 실제 판정은 보류한다.

```json
{
  "users": [
    [
      "A",
      [
        2,
        8
      ]
    ],
    [
      "B",
      [
        3,
        4
      ]
    ]
  ],
  "capacity": [
    1,
    1
  ],
  "cap": 4
}
```

## 5. 기준 방법과 개선 조건

cap 이하 간선만 남긴 뒤 작은 배정 조합을 열거한다. 전체 배정 가능성부터 답한다. 개선은 이분 매칭/최대흐름이며 방문 순서 문제와 다르다.

1순위 도구는 [Python 표준 라이브러리](../../tools/python-stdlib.md)다. 설치 없이 작은 목록·집합·정수 연산으로 시작한다. 실행이 허용되지 않거나 Python이 없으면 후보 표와 손계산을 남긴다. 외부 API·자격증명은 필요 없다. 복잡한 패키지는 데이터 크기와 실패 사례가 기준 방법의 한계를 보여준 뒤 검토한다.

## 6. 최소 구현과 다음 행동

시간행렬·정원 → 가능/불가능과 제한 간선 → 운영자가 정원 조정 또는 추가 지점을 결정한다.

완료 기준은 실제 입력 한 건에서 판정·근거·미확인 사유·다음 행동이 이어지는 것이다. 합성 테스트 통과는 실제 사용자 만족이나 업무 효과를 입증하지 않는다.

## 7. 정상·경계·정보 부족 기대값

| 유형 | 입력 | 기대 결과 | 독립 계산 근거 |
|---|---|---|---|
| normal | `{"users":[["A",[2,8]],["B",[3,4]]],"capacity":[1,1],"cap":4}` | `true` | A→첫지점,B→둘째지점. |
| boundary | `{"users":[["A",[4]]],"capacity":[1],"cap":4}` | `true` | 상한4 포함. |
| missing | `{"users":[["A",[null]]],"capacity":[1],"cap":4}` | `"unknown"` | 이동분 누락. |

[실행 오라클](../../examples/synthetic/check_expansion_c.py)은 각 기대값을 다시 계산한다. 이는 문서 기대값 검증이며 완성 앱·동시 사용자·현장 운영 테스트가 아니다.

## 8. 잘못된 적용과 범위 축소

- 평균이 작다는 이유로 일부 상한 위반을 허용하지 않는다.
- 이 배정을 실제 순회 경로로 해석하지 않는다.

시간이 부족하면 장식·선택 기능을 줄이고 입력 계약, 미확인 처리, 위 기대값 검증을 유지한다. 효과는 동일 업무의 전후 완료 시간·오류 수와 측정 대상 수를 확보한 뒤 판단한다.

## 9. 구현물에 대한 사용자 피드백

1. 불가능한 경우 어떤 정원 또는 상한을 논의해야 하는지 알 수 있는가?
2. 개인별 위반이 평균에 가려지지 않는가?

설명 전에 사용자가 한 건을 처리하게 하고 실패·우회·추가 질문을 관찰한다. 새 요구를 오류 수정·필수 누락·선택 개선으로 분류한다.
