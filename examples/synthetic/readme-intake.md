# README 전체 입력 → 접근 계획 응답 예시

provenance: synthetic. 이 문서의 요청·파일명·필드·제약은 독립 창작이다.
실제 과제 원문이나 이전 업무 요구를 익명화한 것이 아니다. 카탈로그의120개 사례 수에는 합산하지 않는다.
완성 앱·실제 데이터·모델 응답 실행 결과가 아니라 사람이 작성해 정적으로 점검한 입력/응답 예시다.

## 붙여넣는 창작 README

```text
# 작업장 통근 셔틀 조회 웹
사용자: 교대 근무자. 모바일에서 날짜와 근무조를 선택해 기존 운행표를 확인한다.
필수: 노선 목록, 정류장 순서와 예정시각, 운휴 안내, 데이터 없는 경우 안내.
제공 파일: trips.csv, stops.csv, calls.csv.
trips: trip_id, service_date, shift_code, route_name, operating
stops: stop_id, stop_name
calls: trip_id, sequence, stop_id, scheduled_time
시간 표기: 모든 예정시각은 해당 운행일 기준 지역시각 HH:mm이며 이 연습에서는 자정을 넘지 않는다.
조건: 기존 운행표를 조회한다. 노선 변경·실시간 위치·예약·로그인은 요구하지 않는다.
프로젝트: 기존 웹 코드가 있는 허용된 작업 공간에서 작업한다.
제출: 실행 가능한 웹과 실행 방법, 검증 기록.
허용: 제공 코딩 AI와 해당 공간의 파일 읽기·코드 실행. 외부 전송·자동 브라우저 조작 금지.
```

사용자 덧붙임: “approach 저장소를 확인하고 이 제작 요구를 어떻게 진행하면 될지 가이드에 따라 알려줘.”
가정: 이 예시에서는 위 텍스트와 가이드 문서만 읽을 수 있고 실제 CSV·기존 코드는 아직 볼 수 없다.

## 기대되는 첫 응답

이번 작업은 **근무자가 날짜와 근무조에 맞는 기존 셔틀 운행표를 찾는 모바일 웹**입니다.
원문이 노선 변경을 제외했으므로, 먼저 CSV의 관계를 확인하고 날짜·근무조 필터에서 노선 상세까지 연결하겠습니다.
이 단계에서는 접근 계획만 제시합니다.

| 요구 | 구현할 결과 | 검증 기준 |
|---|---|---|
| R1 날짜·근무조 선택 | 선택값에 해당하는 운행 목록 | 다른 날짜·근무조 운행이 섞이지 않음 |
| R2 노선·정류장·예정시각 | 목록→상세, sequence 순 표시 | 입력 파일 행순서가 바뀌어도 정류장 순서 유지 |
| R3 운휴 안내 | 운행 상태가 보이는 목록/상세 | 운휴를 정상 운행으로 표시하지 않음 |
| R4 자료 없음 안내 | 빈 결과와 데이터 오류 구분 | 일치 운행0건과 누락 참조를 같은 상태로 숨기지 않음 |
| R5 실행·인계 | 기존 코드에 연결, 실행법·검증 기록 | 제공된 명령으로 재현 가능 |

노선 변경·실시간 위치·예약·로그인은 원문상 제외입니다.
README 본문은 확인했지만 CSV와 기존 코드는 아직 열지 못했습니다. 실제 행수와 데이터 품질은 미확인입니다.

먼저 볼 자료는 다음3개 묶음입니다.

1. 기존 프로젝트의 실행 설정과 화면 진입점: 사용 중인 프레임워크·실행 명령·수정 위치를 확인합니다.
2. trips.csv: trip_id 중복, 날짜 형식, shift_code 값, operating의 표현과 결측을 확인합니다.
3. calls.csv와 stops.csv: trip_id/stop_id 참조, sequence 중복·정렬, HH:mm 형식을 확인합니다.

담당자에게는 다음을 확인하면 됩니다.

- “운휴편은 목록에 운휴 표시로 남겨야 하나요, 기본 목록에서 제외하고 별도 조회해야 하나요?” → 목록 구성과 필터 정책이 달라집니다.
- “날짜·근무조에 일치하는 운행이0건이면 정상적으로 편성이 없는 경우와 자료 갱신 전인 경우를 어떤 필드로 구분하나요?” → 근거 필드가 없으면 ‘운행 없음’으로 단정하지 않고 ‘등록된 운행 정보 없음’으로 표시합니다.

파일 접근이 가능해지면 위 필드를 먼저 읽고, 파일에 이미 답이 있으면 해당 질문은 생략합니다.

| 순서 | 할 일 | 산출물·완료 기준 |
|---|---|---|
| 1 | 기존 코드 실행법과 CSV 스키마 확인 | 필드·키·시간대·결측 의미가 있는 짧은 데이터 계약 |
| 2 | 실제 운행 한 건을 세 파일로 연결 | 날짜/근무조→노선→정류장 순서·시각까지 일치하는 최소 화면 |
| 3 | 필수 상태 처리 | 운휴·조회0건·참조 오류·필수 값 누락을 구분 |
| 4 | 모바일 목록/상세와 입력 상태 확인 | 좁은 화면에서도 조회·복귀·오류 안내를 수행 가능 |
| 5 | 계산/단위 검사와 허용된 수동 화면 확인 | R1~R5별 실제 결과, 실행 방법과 남은 한계 기록 |

운휴 표시 정책의 답을 기다리는 동안에도 파싱·참조 검증·필터·정류장 정렬 구조는 준비할 수 있습니다.
실제 파일을 못 본 상태에서는 합성 데이터로 연결 실험만 할 수 있고, 이를 실제 데이터 연동 완료로 세지 않겠습니다.
제한 시간이 명시되지 않았으므로 임의의 시험 시간은 가정하지 않겠습니다. 시간이 부족하면 시각 장식부터 줄이고 필수 조회와 오류 구분은 유지합니다.

실행할 검사는 다음과 같습니다. 아직 실행한 결과는 아닙니다.

- 정상: 합성 calls 입력 sequence가 `[3,1,2]`이면 출력은 `[1,2,3]`이며 각 stop_id의 시각이 함께 유지되어야 합니다.
- 경계: 선택한 날짜·근무조에 일치하는 trip이0건이면 명확한 빈 상태를 표시합니다.
- 자료 부족: calls의 stop_id가 stops에 없으면 누락 참조를 알리고 정상 경유지로 확정하지 않습니다.
- 재현: 같은 실제 자료를 다시 읽어도 필터·정렬 결과가 같고, 실행법을 따라 화면을 열 수 있어야 합니다.

참고한 경로는 [최소 경로](../../playbooks/minimum-end-to-end.md), [자료 확인](../../playbooks/evidence-and-data.md), [독립 검증](../../methods/verification.md)입니다.
[MOBILITY 안내](../../families/MOBILITY.md)의 ‘경로가 고정되어 있는가’ 질문을 적용했습니다. 최적화 사례의 목적함수나 합성 제약은 가져오지 않았습니다.
외부 전송·자동 브라우저 조작은 원문에서 금지했으므로 실행하지 않습니다.
다음은 기존 프로젝트와 제공 CSV의 실제 구조를 확인하는 단계입니다.

## 요구가 달라질 때의 분기

- “출발시각을 조정해 근무 시작 전에 도착해야 한다”가 추가되면 [고정 경로 출발시각](../../cases/MOBILITY/mobility-departure.md)의 가능한 구간과 도착 기준을 검토한다.
- “승객을 차량 정원에 맞춰 배정해야 한다”면 용량·탑승 대상·미배정 처리부터 확인한다. 조회 기능만으로 요구를 충족했다고 하지 않는다.
- “정류장 방문 순서를 바꿔라”면 [방문 순서](../../cases/MOBILITY/mobility-tour.md)를 읽고 시간 행렬·시간창·복귀 조건을 확인한다.
- “분석 보고서만 제출한다”면 화면 제작 대신 기존안/대안·지표·필수조건 위반표를 만든다.
- 원문에 모든 정책·데이터·허용 범위가 충분히 명시되어 있으면 질문을 만들기 위해 질문하지 않는다.
- 실제 AI 금지 평가 단계라면 위 예시 응답이나 분기 질문을 생성하지 않고 지원을 중단한다.
