# 구현물을 사용한 업무 피드백

이 문서는 사용자가 업무를 수행할 수 있는지 관찰하는 절차다. 개발자의 설명 연습은 [별도 흐름](rehearsal-only.md)으로 진행한다. [규정](../RULES_GATE.md)이 허용하는 TASK 또는 PREP에서만 사용한다.

## 관찰 순서

1. 허용된 입력 한 건과 수행할 업무를 제시한다. 조작법을 먼저 설명하지 않는다.
2. 사용자가 완료·중단·우회하는 지점, 오류, 도움 요청을 기록한다.
3. 결과를 본 다음 무엇을 할지 묻는다. 판단 근거와 unknown 표시를 실제로 이해했는지 확인한다.
4. 필요하면 조작법을 설명한 뒤 두 번째 시도를 관찰한다. 첫 사용과 교육 후 결과를 섞지 않는다.

## 질문 카드

| ask_when | target | question | why | expected_evidence | changes_plan | stop_condition |
|---|---|---|---|---|---|---|
| 결과 한 건 생성 | 업무 담당자 | 이 결과를 사용하시겠습니까? 달라져야 한다면 어떤 근거 때문입니까? | 판정 정합성 | 입력·출력·적용 정책 | 규칙 오류 수정 | 수용 또는 수정 근거 확보 |
| 화면에서 멈춤 | 첫 사용자 | 지금 무엇을 하려고 했습니까? | 의도와 UI 비교 | 클릭·중단·우회 관찰 | 명칭·동선 조정 | 의도와 장애 확인 |
| 확인 불가 표시 | 업무 담당자 | 이 상태를 받으면 다음에 누구에게 무엇을 확인하겠습니까? | 보류의 실행 가능성 | 실제 다음 행동 | 보류 사유·담당 안내 보완 | 실행할 행동 확인 |
| 새 기능 요청 | 요청 책임자 | 이 기능이 없으면 어떤 필수 업무를 완료할 수 없습니까? | 범위 관리 | 기존 완료 기준 | 필수 누락/선택 개선 분리 | 영향과 우선순위 기록 |

## 변경 판단

[피드백 기록](../templates/feedback-log.md)에 관찰과 발언을 분리한다. 오류 수정은 기존 기대와 다른 동작, 필수 누락은 합의된 기준의 미구현, 선택 개선은 추가 가치다. 각 변경의 시간 비용과 기존 기준 영향을 적는다. 모든 발언을 새 기능으로 구현하지 않는다.

모의 담당자는 가설 확인용이다. 실제 사용자 만족이나 업무 효과를 검증했다고 기록하지 않는다.
